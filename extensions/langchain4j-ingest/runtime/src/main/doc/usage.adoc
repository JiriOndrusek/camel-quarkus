=== Ingesting a directory

Point a pipeline at a folder and the files in it become a knowledge base. No route, no ingestion code:

[source,properties]
----
quarkus.camel.ai.ingest.products.source.directory=/var/data/product-docs
quarkus.camel.ai.ingest.products.embedding-store=products
quarkus.camel.ai.ingest.products.embedding-model=my-model
----

Documents are read as text — there is no format parsing, so a PDF or DOCX must be converted before it reaches a pipeline. Each file is read as UTF-8, split into overlapping segments (`max-segment-size` and `max-overlap-size`), embedded in batches and written to the store. `embedding-store` and `embedding-model` name CDI beans and may be omitted when the application has exactly one of each; with several, naming one is required rather than guessed. Each document is held in memory whole while it is split, so mind the size of what lands in the directory.

Every property except `enabled` and the `source.*` runtime ones is fixed at build time. A pipeline may be declared purely at runtime — a directory is enough — but build-time properties such as `max-segment-size` or `embedding-store` set only at runtime are ignored (Quarkus logs its generic changed-at-runtime warning) and the pipeline runs with the defaults.

Every segment carries `camel_quarkus_pipeline` and `camel_quarkus_document_id` metadata, so retrieval can cite which document an answer came from.

[NOTE]
====
This preview ingests what it is given and keeps no record of it, so a document ingested twice leaves two copies in the store. That has consequences worth planning around: a restart re-reads the whole directory, because the file consumer's duplicate protection is an in-memory register (sized for 100,000 files) rather than a persisted one; and a polled consumer such as `aws2-s3` with `deleteAfterRead(false)` re-reads every object on every poll, growing the store without bound. Ingest into a store you can rebuild, or keep the polling interval long, until the synchronising engine lands. Keeping a store in step with a changing source — skipping unchanged documents, replacing edited ones and removing deleted ones — needs that record, and arrives in a later release.
====

=== Any other source

Beyond a directory, a pipeline reads from any Camel consumer at all — the roughly 300 components, with their own option names, their own defaults and their own documentation. The way to reach them is the Endpoint DSL, so the options are typed rather than spelled into a URI:

[source,java]
----
@Ingest("product-docs")
IngestPipeline productDocs() {
    return IngestPipeline.from(Source.endpoint(dsl -> dsl.aws2S3("product-docs")
            .region("eu-west-1")
            .deleteAfterRead(false))
            .documentId("CamelAwsS3Key"))
            .embeddingStore("products");
}
----

Nothing is imported: typing `dsl.` lists a factory for every Camel component, and each completes its own options. `Source.endpoint(aws2S3(...))` with a static import of `StaticEndpointBuilders` is the same DSL for those who prefer it.

[NOTE]
====
Mind each component's own defaults: the `aws2-s3` consumer *deletes objects after reading them* unless `deleteAfterRead(false)` is set, which is why every example here sets it. A knowledge base reads its source, it does not consume it.
====

Ingestion needs a stable id per document, and where that id lives is the consumer's business: the object key for S3 (`CamelAwsS3Key`), the record key for Kafka (`CamelKafkaKey`), a header your own route sets. `documentId` names it. Without it, the pipeline expects the `CamelIngestDocumentId` header and fails the exchange when it is absent.

Setting `source.uri` is what makes a pipeline consume from a component rather than read a directory — there is no source type to declare. The URI is build-time by design — a runtime-overridable consumer URI would be arbitrary component invocation. Property placeholders inside it still resolve at startup, so credentials and endpoints stay runtime configuration:

[source,properties]
----
quarkus.camel.ai.ingest.custom.source.uri=direct:custom-source
quarkus.camel.ai.ingest.custom.source.document-id=CamelAwsS3Key
----

Give `document-id` a header name, or a full simple-language expression when the id is not a plain header — though in a properties file `${...}` is expanded by MicroProfile Config before Camel sees it, so the bare header name is the form to prefer there.

Runtime configuration is a trust boundary, the same one it is for any Camel application: `source.directory` decides which files the process reads into an (often external) store, and a `document-id` expression can read system properties or environment variables. Whoever can change runtime configuration can therefore direct what is ingested and how it is identified — treat that configuration with the same care as the consumer URI, which is fixed at build time for exactly this reason.

After a consumer-fed pipeline ingests a document, the exchange body is replaced with the `IngestResult` — the pipeline, the document id, how many segments were written and the outcome — so a request-reply caller (`direct`, `platform-http`, …) receives the outcome of its call. A directory pipeline discards the result, as there is nobody to reply to.

=== When ingestion fails

A failure while splitting, embedding or storing — a rate-limited model, an unreachable store — propagates to the consumer; there is no dead-letter channel in this increment. For a directory pipeline the file stays where it is and is retried on the next poll, because the duplicate-protection key is only committed on success — which also means a permanently failing file is retried forever, loudly. For a consumer-fed pipeline the component's own error handling applies: a request-reply caller receives the exception, while a Kafka consumer with default settings logs the failure and commits the offset, so the record is *dropped* — and since this engine keeps no record either, nothing remembers it. A record whose configured `document-id` resolves to nothing (a Kafka record without a key, say) fails the same way, one exchange at a time.

=== Declaring a pipeline in Java

Every property has a builder twin, for those who prefer IDE completion to property names:

[source,java]
----
@Ingest("datasheets")
IngestPipeline datasheets() {
    return IngestPipeline.from(Source.endpoint(dsl -> dsl.aws2S3("product-docs").region("eu-west-1").deleteAfterRead(false))
                    .documentId("CamelAwsS3Key"))
            .embeddingStore("products")
            .splitter(500, 50);
}
----

`Source` offers the same source three ways, and the lambda above is the one to reach for: `dsl.` lists a factory for every Camel component and each completes its own options, with nothing to import and nothing to look up. `Source.endpoint(aws2S3(...))` is the identical DSL through a static import of `StaticEndpointBuilders`, and `Source.endpoint("aws2-s3://…")` takes a raw URI for the cases where one is assembled at runtime. `Source.file` is the shorthand for a directory, and `.documentId(...)` names the id in every case.

Sharp edge worth knowing about the first two: the DSL factories all ship in one artifact, so the call compiles even when the connector extension is absent — the missing component is then reported at startup.

`@Ingest` methods must return `IngestPipeline`, take no parameters and carry a name that no configuration-declared pipeline already uses — all three are build failures otherwise.
