# Fix plan: Native test failure in integration-tests/pqc

## Problem
The PQC extension passes all 6 tests in JVM mode but fails 3 tests (testKemEncapsulationWithKyberAes, testKemExtractToHeaderWithKyberChacha, testKemExtractToHeaderWithKyberAes) in native mode with HTTP 500 errors. The underlying cause is a `java.lang.SecurityException` thrown when the native application attempts to use KYBER key encapsulation algorithms at runtime. The error message explicitly states: "Attempted to verify a provider that was not registered at build time: BCPQC version 1.83. All security providers must be registered and verified during native image generation."

## Root cause
GraalVM's security provider verification requires all Java security providers to be registered and verified during the native image build process, not just at runtime. The PQC extension currently registers the Bouncy Castle Post-Quantum Cryptography (BCPQC) provider at runtime via `PqcRecorder.java` using `STATIC_INIT`, but this is insufficient for native compilation. GraalVM needs a build-time declaration via `NativeImageSecurityProviderBuildItem` to include the provider in the native image's security provider registry. The three signature-based tests (Dilithium, Falcon, SPHINCSPlus) pass because they follow different code paths that don't trigger GraalVM's strict provider verification, while KYBER KEM operations explicitly verify the provider, exposing the missing build-time registration.

## Proposed fix
1. Add a new `@BuildStep` method to `extensions/pqc/deployment/src/main/java/org/apache/camel/quarkus/component/pqc/deployment/PqcProcessor.java`
2. The build step should return a `NativeImageSecurityProviderBuildItem` configured with the fully-qualified class name of the BCPQC provider
3. Remove the commented-out workaround from `integration-tests/pqc/src/main/resources/application.properties` if present (the proper fix makes it unnecessary)
4. Follow the same pattern used in `extensions/kudu/deployment/src/main/java/org/apache/camel/quarkus/component/pqc/deployment/KuduProcessor.java` for security provider registration
5. No conditional logic is needed - the provider should always be registered when the PQC extension is present

## Files to change
| File | What to change |
|------|---------------|
| `extensions/pqc/deployment/src/main/java/org/apache/camel/quarkus/component/pqc/deployment/PqcProcessor.java` | Add a new `@BuildStep` method named `registerBcpqcSecurityProvider()` that returns `new NativeImageSecurityProviderBuildItem("org.bouncycastle.pqc.jcajce.provider.BouncyCastlePQCProvider")` |
| `integration-tests/pqc/src/main/resources/application.properties` | Remove the commented line `#quarkus.native.additional-build-args=-H:AdditionalSecurityProviders=BCPQC` if it exists (the build item replaces this workaround) |

## Edge cases to consider
1. **Provider version specificity**: The error mentions "BCPQC version 1.83" but the fix uses the provider class name without version. This is correct - GraalVM determines the version from the loaded provider instance.
2. **Dependency on standard BC**: Verify that BCPQC provider doesn't conflict with standard Bouncy Castle (BC) provider registration in `extensions-support/bouncycastle`. These are separate providers and should coexist without issues.
3. **Multiple provider registrations**: Ensure no duplicate registration if the extension is included multiple times in different modules - GraalVM handles duplicates gracefully, but verify no warnings appear.
4. **Resource bundles**: Monitor for potential `MissingResourceException` errors during native tests. BCPQC might require security resource bundles (like `sun.security.util.resources`) which would need `NativeImageResourceBundleBuildItem` registration.
5. **Provider initialization order**: The existing `PqcRecorder` runtime registration at `STATIC_INIT` should remain - it complements the build-time registration and handles provider initialization.

## Issues found

1. **Incorrect algorithm instantiation in PqcRecorder** (minor, non-breaking):
   - `PqcRecorder.java:46-56` attempts to instantiate "Kyber" as a Signature algorithm via `Signature.getInstance("Kyber", provider)`
   - Kyber is a KEM algorithm, not a digital signature algorithm - this instantiation will always fail
   - The failure is caught and logged, so it's harmless, but the "Kyber" entry in the transformations list (line 92) serves no purpose
   - Only "KyberKeyPairGenerator" is needed since Kyber is accessed via `KeyPairGenerator.getInstance("Kyber", "BCPQC")` as shown in `PqcResource.java:84`

2. **Potentially incorrect index dependency** (needs verification):
   - `PqcProcessor.java:50-52` indexes `"org.bouncycastle", "bcprov-jdk18on"` artifact
   - This is the standard Bouncy Castle provider, not the PQC-specific one
   - Should verify if this should be `"org.bouncycastle", "bcpqc-jdk18on"` instead, or if both are needed

3. **No negative test cases**:
   - All tests verify happy paths only (successful sign/verify, encapsulate/extract)
   - No tests for invalid signatures, tampered encapsulations, or mismatched keys
   - Not a blocker but reduces confidence in error handling

## Code quality observations

**Positive**:
- Clean separation of concerns: deployment processor handles build-time registration, recorder handles runtime initialization
- Comprehensive reflection registration for PQC classes in `registerBouncyCastlePQCClasses()` with appropriate filters
- Proper shutdown handling with provider removal in `PqcRecorder.java:64-70`
- Test structure correctly follows Quarkus patterns (`@QuarkusTest` for JVM, `@QuarkusIntegrationTest` extending base class for native)

**Observations**:
